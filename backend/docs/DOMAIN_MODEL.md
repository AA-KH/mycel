# Domain Boundaries and Models

This document strictly defines the core concepts and boundaries of the Mycel architecture. These entities describe the ontological structure of the system, preventing conceptual leakage (e.g., treating a generic "Role" as an "Employee").

## Organizational Entities

### Company
- **Definition**: The root organizational structure.
- **Responsibility**: Owns and groups multiple Teams and Departments. Maintains global configurations.

### Team
- **Definition**: A distinct functional unit within the Company (e.g., "Engineering", "Marketing").
- **Responsibility**: Contains Employees and groups relevant Positions. Often acts as a boundary for shared context or budget.

### Position
- **Definition**: A job title and its associated baseline requirements (e.g., "Senior Researcher").
- **Responsibility**: Describes the job that needs to be done. 
- **Rule**: A Position is NOT an Employee. Multiple Employees can hold the same Position, but they will have different skills and reasoning profiles.

## Identity Entities

### Employee
- **Definition**: A unique, persistent AI identity (e.g., "Aarav Mehta").
- **Responsibility**: Represents a specific "person" in the system with their own name, personality, experience level, skill set, and performance history.
- **Rule**: Employee != Position. Employee Identity != Role.

### AgentDefinition
- **Definition**: The static configuration schema of an Employee.
- **Responsibility**: Defines how an employee behaves, what tools they can use, and their reasoning profile, before they are actually instantiated in memory.
- **Rule**: AgentDefinition != Agent Runtime. The definition is the blueprint; the runtime is the engine that executes the blueprint.

### ReasoningProfile
- **Definition**: The structured cognitive strategy for an Employee.
- **Responsibility**: Defines the exact sequence of lifecycle steps an employee takes to solve a task. (e.g., A Researcher's profile is `research -> collect -> validate -> cite`, while a Developer's is `inspect -> design -> implement -> test`).

## Competency Entities

### Skill
- **Definition**: A quantifiable capability of an Employee (e.g., "Data Analysis: 91", "FastAPI: 98").
- **Responsibility**: Used by the Hiring System to calculate matches against task requirements.
- **Rule**: Skill != Tool. Knowing "Video Editing" is a skill; "FFmpeg" is a tool.

### Tool
- **Definition**: An executable function or capability (e.g., "web_search", "python_repl").
- **Responsibility**: Allows the Agent Runtime to interact with external systems. 
- **Rule**: Tool != ToolPermission.

### ToolPermission
- **Definition**: An authorization grant.
- **Responsibility**: Dictates whether a specific Employee is allowed to execute a specific Tool, often tied to a cost constraint or security risk level.

## Execution Entities

### Project
- **Definition**: A large, multi-step objective submitted by the user.
- **Responsibility**: Contains the root goal and manages the overarching state of multiple Tasks.

### Task
- **Definition**: A discrete, assignable unit of work.
- **Responsibility**: Represents the work to be done. A Task is assigned to an Employee by the Orchestrator.

### TaskNode
- **Definition**: A node within a DAG (Directed Acyclic Graph) of a Project.
- **Responsibility**: Represents task dependencies. Task B cannot start until TaskNode A is completed.

### Artifact
- **Definition**: The physical, verifiable output of a Task.
- **Responsibility**: Represents the actual output (e.g., a `.mp4` file, a `.md` report, a code snippet). 
- **Rule**: A task is ONLY successful when the Artifact is physically verified and stored, NOT just when the LLM says "Task completed."

## Hiring & Performance Entities

### HiringRequest
- **Definition**: A structured query generated by the Orchestrator based on a Task's requirements.
- **Responsibility**: Represents a requirement for an employee (e.g., "Needs 90+ Python skill, authorized for Docker tool").

### Candidate / Interview / Assessment
- **Definition**: Ephemeral states during the smart hiring process.
- **Responsibility**: Used to evaluate, rank, and select the best Employee from the talent pool for a specific HiringRequest.

### PerformanceRecord
- **Definition**: A historical log of an Employee's task outcomes.
- **Responsibility**: Tracks success rates, artifact quality, and execution speed.

### Evaluation
- **Definition**: A qualitative and quantitative score given to an Artifact or Reasoning trace.
- **Responsibility**: Drives the `PerformanceRecord` and triggers `Upskill` events if an Employee consistently performs well.

### Memory
- **Definition**: Contextual storage.
- **Responsibility**: Allows Employees to retain and retrieve information across Tasks (short-term) and Projects (long-term).
